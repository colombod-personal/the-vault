# Verification ledger (issue #242)

What the product owner asked for, issue by issue, and what was found when each criterion was checked against the code,
the tests and the live service. Written because merged work had been called done without evidence.

**Method.** Six read-only audits on a frozen copy of `main` (commit 6dc997f, 2026-10-07). For every closed-or-merged issue
the audit took the owner's words and the issue's acceptance criteria, added the criteria a reader would reasonably
derive, and for each one found the test or document that proves it, or said it did not exist. Nothing was taken from a
pull request description. "Test" means a named test that passes in CI; "doc only" means a design or record that exists
but nothing executes it; "needs a real run" means only a person's browser, Claude, ChatGPT or production can show it.

**Totals: 78 issues, 563 criteria.** Test-proven: 240. Document only: 147.
Superseded by a recorded owner decision: 12. Needs a real run: 71.
**Not met: 93.**

An issue is `Verified` only when every criterion is test-proven, documented or superseded. Everything else stays open
in GitHub with its failed criteria listed in a comment, until the criterion is met and shown.

### #3 Auth hardening: rate limits, passkey user verification, Facebook deletion replay

| Criterion | Source | Result | Evidence / why |
|---|---|---|---|
| No rate limits on auth endpoints: per-IP limit (edge or in the app) | issue | test | tests/test_rate_limits.py::test_every_sign_in_endpoint_is_limited — Parametrized over 13 sign-in endpoints (passkey x6, native, token, OAuth login/callback, Facebook x2): second call is 429 with Retry-After. Limiter is in the app (vault/ratelimit.py, Postgres counters), not at the Vercel edge. The endpoint list is hard-coded, not derived from the router, so a new auth route is not covered automatically.
